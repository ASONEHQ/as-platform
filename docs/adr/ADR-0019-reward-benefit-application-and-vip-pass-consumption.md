# ADR-0019: Reward benefit application, checkout pricing integration, and settlement-only VIP Pass consumption

- Status: Accepted
- Date: 2026-09-07
- Owners: AS ONE Engineering
- Supersedes: none (extends ADR-0016, ADR-0018)

## Context

ADR-0018 (TASK 13.1) built a complete reward entitlement/redemption engine — issuance, expiry, revocation, standalone `POST /reward-entitlements/{id}/redeem` — but explicitly deferred the one piece that makes a VIP Pass actually worth anything at the register: *"applying the redeemed reward's actual commercial benefit at the POS... is EXPLICITLY DEFERRED — no canonical pricing-integration rule exists yet for how a redeemed entitlement should interact with `promotions`/`pricing.service.ts` at checkout"* (ADR-0018 D11).

TASK 13.2 is that deferred work: a customer with an AVAILABLE VIP Pass attaches it during checkout, sees its real benefit in the quote, the benefit survives into the created Sale, and the entitlement is consumed **exactly when, and only when, the Sale genuinely settles** — never on a mere quote, never on a pending/abandoned/cancelled Sale, never twice under concurrent settlement.

Forensic reconciliation against ADR-0016 (`pricing.service.ts`'s existing catalog → promotion → coupon → manual → tax pipeline), ADR-0017/ADR-0018 (loyalty/reward data model), `CORE_DATA_MODEL.md`, and `API_CONTRACTS.md` preceded any code change, per this task's own explicit instruction not to assume the pipeline placement or benefit shape in advance.

## Decisions

### D1 — Reward benefit model: four typed benefit kinds, stored on the program, never arbitrary executable JSON

`loyalty_programs` gains three new columns — `reward_benefit_type` (a closed enum: `percentage_discount | fixed_amount_discount | fixed_price | free_eligible_item`), `reward_benefit_percentage_basis_points`, `reward_benefit_fixed_amount` — mirroring `promotions`' own established `benefit_percentage_basis_points`/`benefit_fixed_amount` mutual-exclusion pattern (ADR-0016 D3) rather than inventing a parallel shape. A DB `CHECK` constraint enforces exactly one value populated per type (percentage↔basis-points, fixed_price/fixed_amount_discount↔fixed-amount, free_eligible_item↔neither), and a second `CHECK` requires `reward_type` to be set whenever `reward_benefit_type` is (a benefit with nothing to attach it to is meaningless). No free-text or JSON "rule" column exists — the four kinds are the complete, closed set this task actually needs, matching ADR-0018 D3's own "smallest typed set, no rule DSL" precedent for `reward_type` itself.

### D2 — Benefit scope: real relational join tables, and — deliberately — the INVERSE of promotion's own empty-scope convention

`loyalty_program_reward_products`/`loyalty_program_reward_categories` mirror `promotion_products`/`promotion_categories` (ADR-0016) exactly: real join tables, never a denormalized array or JSON column. Where they deliberately diverge from that precedent: `promotions`' own scope treats "both empty" as "applies to everything" (a promotion with no explicit restriction is a store-wide promotion); a reward's scope treats "both empty" as **matches NOTHING**. A loyalty program's reward benefit is a company-configured, deliberate grant tied to specific products/categories (e.g. "VIP Pass waives one admission") — an accidentally-unscoped reward silently discounting an unrelated product family (socks, drinks, a membership fee) is a real commercial risk a promotion's own broader "store-wide sale" semantics doesn't carry. Enforced in two independent places (defense in depth, matching ADR-0017 D21's own convention): the pricing engine's `isLineEligibleForReward` never falls back to "everything" on an empty scope, and `LoyaltyService.createProgram`/`updateProgram` reject `reward_benefit_type` being set with an entirely empty scope at the service layer, before the row is ever written.

### D3 — Pricing pipeline placement: step "2.5", between coupon and manual discount — reusing the coupon's own cascading-and-capping mechanism, not a new stacking schema

`pricing.service.ts`'s `evaluatePricing` gained exactly one new step, inserted after coupon evaluation and before the manual discount:

```
catalog price → automatic promotions → coupon → REWARD BENEFIT → manual discount → tax → total
```

The reward is computed against `remainingAfterCouponsUnits` — the exact same "capped at what's actually left, never negative" running-remainder array coupons already populate — so it "stacks" with promotions and coupons for free, through a mechanism already proven correct (ADR-0016), rather than a new explicit combinability schema. It is placed **before** the manual discount for two concrete reasons: (1) a cashier's existing `discount.apply` override authority (ADR-0016 D11) must still operate on top of whatever the reward already granted, never be blocked by it; (2) the reward's own benefit must never be starved to zero by a manual discount that already consumed everything remaining on the line first. No new `reward_combinable_with_promotions`/`_coupons`/`_manual` flags were added — the task's own instruction was to "prefer minimal explicit rules," and the cascading placement already produces sane, deterministic, auditable behavior without one. If a future program genuinely needs to REJECT stacking (e.g. "this reward cannot combine with any active coupon"), that is a real, separate typed policy for a later pass — not silently assumed here.

### D4 — Partial benefit: one entitlement, one benefit event, on exactly ONE line — uniformly across all four benefit types

A cart with several eligible lines (e.g. three admissions in scope) never has a single entitlement silently discount all three. `computeRewardBenefit` selects exactly one eligible line — the one with the **largest remaining amount** (most beneficial to the customer, and a deterministic pick when several tie) — and applies the entire benefit there. This is deliberately uniform across all four benefit types, not special-cased for `free_eligible_item` alone: a `percentage_discount`/`fixed_price`/`fixed_amount_discount` reward is exactly as single-line-scoped as a "free item" one. A line already reduced to `0` by an earlier promotion/coupon is correctly excluded (nothing remains to benefit).

### D5 — Quote previews, sale creation re-validates and freezes; neither ever mutates the entitlement

`RewardsService.resolveCheckoutBenefit(context, customerId, rewardEntitlementId, now)` is the single place a reward's checkout benefit is resolved: read-only (no row lock, no write), requires `reward.redeem`, checks `effectiveStatus()` (ADR-0018 D9 — never the raw persisted `status`), and validates the entitlement's own program actually has a benefit configured. It is called from **both** `PromotionsService.quote()` and `SalesService.createSale()` — the same function, not two independently-drifting checks. A quote can be requested any number of times and never changes any persisted reward state (proven directly — see Validation). Sale creation calls the identical resolver fresh (never trusts a client-supplied prior quote result — Part D's explicit "re-validated fresh here" requirement) and, only if the pricing engine's own cascade actually produced a nonzero reward discount, writes a durable snapshot (D6). A `pending_payment` Sale — one that was created but never settled — has, by construction, never called anything that redeems the entitlement.

### D6 — Sale reward snapshot: a hybrid of the existing `sale_discounts` arithmetic authority and a new, purely lifecycle-tracking `sale_reward_usages` table

Two things needed recording, and they are kept genuinely separate rather than invented twice: **the money** (how much was discounted, on which line) and **the lifecycle** (has this reward's use on this Sale been applied / consumed / released). The money reuses the existing, already-proven `sale_discounts` table exactly as-is — its `source_type` `CHECK` was widened to also accept `'reward'` (alongside `promotion`/`coupon`/`manual`), so a reward-sourced discount is one more row in the SAME table `sales`/refunds already treat as the one authoritative discount ledger, never a second, parallel arithmetic source that could drift from it.

`sale_reward_usages` is new, and deliberately does none of that arithmetic itself — `benefit_amount_snapshot` on it is an explicit, documented **read-convenience copy** of the same number already committed to `sale_discounts`, never a second authority. What it uniquely owns is a small state machine — `applied → consumed | released` — with a `UNIQUE(company_id, sale_id)` constraint (exactly one reward usage per Sale, matching the POS UX's own "cashier selects one reward" scope) and FKs to the Sale, the Sale Item, the reward entitlement, and the loyalty program, so a historical Sale's reward context remains fully reproducible even if the program/reward/customer/entitlement is later changed, renamed, or reconfigured (Part G's own explicit "must remain reproducible" requirement).

### D7 — Settlement-only consumption: the entitlement is redeemed inside the SAME atomic transaction that settles the Sale, by reusing ADR-0018's already-concurrency-proven row lock — never a new reservation mechanism

This is the load-bearing decision of the whole task. At Sale **creation**, a `sale_reward_usages` row is written `status='applied'` — and this is explicitly allowed to happen for **multiple competing Sales** referencing the same entitlement; there is no uniqueness constraint across Sales for one entitlement, only one row per Sale. Nothing about creating a Sale reserves, locks, or consumes anything on the entitlement itself.

At **settlement** — inside `PaymentService.applyPostSettlementHooks`, the exact same database transaction `SalesRepository.trySettleSale` already uses to flip a Sale to `completed` (the identical hook point ADR-0018 D6 established for automatic reward *issuance*, now used for reward *consumption* too) — `RewardsService.consumeAppliedUsagesForSale(client, context)` locks that Sale's `applied` usage row(s), then locks the underlying entitlement via `RewardsRepository.lockEntitlement`'s `SELECT ... FOR UPDATE` — **the identical row-lock mechanism ADR-0018 D10 already built and already proved safe under real concurrency for the standalone `/redeem` endpoint** — and calls the same `markRedeemed`. No new reservation table, no new advisory lock, no new optimistic-version scheme was invented for this: the entitlement itself, locked exactly the way it already was, is the one and only mutual-exclusion point.

Whichever Sale's settlement transaction acquires that lock first and finds the entitlement still `available` wins and commits (Sale completes, entitlement redeemed, usage row `consumed`). Any other Sale racing the same entitlement finds it already `redeemed` once it acquires the lock, and `consumeAppliedUsagesForSale` **throws** — which, because this all happens inside `trySettleSale`'s own transaction, rolls back the *entire* settlement attempt: no payment is left in a half-completed state, the Sale does not become `completed`, and no cash/card money is taken for a benefit that didn't actually apply (Part F's explicit "no payment irreversibility risk"). The losing Sale's own `sale_reward_usages` row is left exactly as it was (`applied`) — it was never consumed, so there is nothing to "give back."

One deliberate simplification: unlike the standalone `redeem()`'s special "persist the expiry transition, then throw after commit" trick (ADR-0018 D14), `consumeAppliedUsagesForSale` does **not** attempt to persist a lazy `available → expired` transition on rejection — doing so inside an already-failing settlement transaction would require partially committing while the rest rolls back, breaking atomicity for no real benefit. This is safe because `effectiveStatus()` (ADR-0018 D9) always computes the correct live answer regardless of whether the row's *persisted* status has caught up yet — the next real interaction with that entitlement (a fresh redeem attempt, a fresh sale-creation-time validation) will see and correctly persist the expiry itself.

### D8 — Concurrency: proven directly, not assumed from the mechanism's provenance alone

Reusing a proven lock is a strong argument, not a substitute for proof at the new call site. TASK 13.2's own integration test suite races two independently created Sales against the same entitlement through real concurrent settlement calls (`Promise.allSettled`, each on its own connection/transaction — see `payments.integration.test.ts`/`sales.integration.test.ts`) and asserts: exactly one Sale reaches `completed`, the entitlement is `redeemed` exactly once, exactly one `sale_reward_usages` row reaches `consumed`, and the losing Sale is left in a clean, non-corrupted, non-`completed` state with no orphaned payment row. Mercado Pago's own webhook-driven settlement path is currently PAUSED (unrelated to this task) — its interaction with this same lock is a documented open question or a future pass, not exercised here, since no live MP settlement can occur while paused.

### D9 — Zero-total sales settle through a dedicated, explicit path — never a fake payment

A reward (or reward + coupon + promotion combination) can legitimately bring a Sale's `total` to exactly `0`. Two existing mechanisms were confirmed, by direct code reading before writing anything new, to already make this reachable without inventing new arithmetic: `SalesRepository.trySettleSale`'s own settlement condition (`capturedTotal >= total`) is already satisfied by `0 >= 0` with **zero** payment rows; `PaymentService.createCashPayment`, however, already and correctly *rejects* a zero-remaining-balance sale outright (there is nothing to tender). Rather than coerce a fake `$0.00` cash tender through the existing cash path (explicitly forbidden by the task), a new, narrow `PaymentService.completeZeroTotalSale(context, branchIds, saleId)` method was added: it locks the Sale, validates `total === 0` and `status === 'pending_payment'`, calls `trySettleSale` directly — creating **no** payment, payment-attempt, or cash-movement row of any kind — runs the same `applyPostSettlementHooks` (reward consumption, loyalty earning, automatic issuance, exactly as any other settlement), and writes a **distinct** `sale.completed_without_payment` audit/outbox event alongside the normal `sale.completed`, so audit trails and any downstream cash-drawer reconciliation can tell "settled with real tender" apart from "settled because the total was genuinely zero" — never silently conflating the two. Exposed as `POST /sales/{sale_id}/zero-total-completion`, gated by `reward.redeem` (no new permission — see D-Permissions below). Deliberately not idempotency-key-gated: the request carries no variable caller-supplied data to hash, and `trySettleSale`'s own repeat-settlement-safety already covers a retried call.

### D10 — Reward QR scan attaches an INTENT; it is never itself a redemption

ADR-0018 D12 already established `reward_entitlement_tokens` as a presentation-token concept distinct from the customer's own QR. This task does not change that token mechanism, but it does fix the semantics of what scanning one means at checkout: resolving a presentation token (the existing `POST /reward-entitlements/resolve-token` from ADR-0018) identifies WHICH entitlement the cashier is about to use — it is the equivalent of the cashier picking it from a list — and the resulting `rewardEntitlementId` is attached to the in-progress quote/Sale exactly like any other reward selection. Nothing about scanning, resolving, or attaching a token calls `redeem()` or writes anything to `sale_reward_usages` with `status='consumed'`. The actual redemption only ever happens through D7's settlement-time consumption — a scanned-and-attached-then-abandoned Sale leaves the entitlement completely untouched, identical to a reward selected by tapping it in a list and then never checking out.

### D11 — Receipt and history surface the reward generically, through the same mechanism that already surfaces promotions/coupons/manual discounts — no new formatting code, no PII

Because the reward's discount is a normal `sale_discounts` row (D6), the existing generic discount serialization in `sales.routes.ts` (`source_type`/`source_id`/`label`) already surfaces it on receipts and in Sales History with **zero new formatting code** — the pricing engine sets `label: 'Recompensa'` and `sourceId: <the entitlement id>`, never a phone number, email, or presentation token. A historical receipt reprint remains byte-for-byte reproducible from the Sale's own frozen `sale_items`/`sale_discounts` rows (D6, D-Refunds below) even if the originating loyalty program's benefit configuration is later changed or removed — nothing about reprint re-reads live program configuration. A dedicated Customer-Detail "this entitlement was redeemed by Sale X" view is **not yet exposed** by a new endpoint in this backend pass — the durable link exists in the data model (`sale_reward_usages.sale_id`, queryable today) and is available to build against, but surfacing it in the Customer Detail read path is left to the Flutter/API-surface work tracked separately (see Deferred).

### D12 — Refunds: already correct by construction, verified rather than modified

`RefundsService`'s line-reversal math (`computeLineReversal`) recomputes a refund entirely from the Sale Item's own **frozen** `discountBasisPoints` — the generic, source-agnostic rate `evaluatePricing`'s final fold step (ADR-0016) already writes onto every line regardless of which pipeline step produced the discount. Because a reward-sourced discount folds into that exact same generic `discountUnits`/`discountBasisPoints` computation (D3), refund math for a reward-discounted Sale required **no code change at all** — confirmed by direct reading of `refunds.service.ts` before writing this ADR, and by a regression test exercising a refund against a reward-discounted Sale. `RefundsService` has zero awareness of `reward_entitlements`/`sale_reward_usages` — a refund never reactivates, revokes, or otherwise touches the underlying entitlement; it remains consumed after a refund, matching ADR-0018 D16's identical "no automatic reward reversal on refund" stance, extended here to the benefit-application layer for the same reason: no canonical business rule for "should a refunded purchase un-consume the reward it used" exists, and inventing one is out of scope. If a business needs to manually correct this, that remains outside this task, exactly as ADR-0018 already documented.

### D13 — No backfill: this task only ever touches Sales created going forward

Every existing Sale, `sale_discounts` row, and `reward_entitlements` row that predates this task is left completely untouched — no migration populates `sale_reward_usages` for historical Sales, no existing redeemed entitlement is retroactively linked to a Sale it was actually used on before this feature existed (that link was never recorded and cannot be honestly reconstructed). Historical Sales simply have no reward usage snapshot, exactly as before.

### D14 — External payment-provider reconciliation risk (documented, not resolved): Mercado Pago remains paused

D7's lock-and-consume mechanism runs inside the same transaction as `trySettleSale` regardless of which payment path triggers settlement, so a Mercado Pago webhook-driven settlement would, structurally, go through the identical `applyPostSettlementHooks` call and the identical lock. What is NOT exercised or proven by this task is the specific failure mode where an external provider (Mercado Pago) reports a payment as captured, its webhook fires settlement, and reward consumption then fails (lost the concurrency race) — at that point the *money* has already moved at the provider, but the *Sale* cannot settle, an asymmetry cash payments do not have (a cash payment that fails to settle simply never took the cash). This is a genuine, undismissed reconciliation risk for a future live-MP pass to design for explicitly (e.g. an automatic void/refund-back path, or a manual reconciliation queue) — it is not silently assumed safe here, and it does not need to be resolved now because Mercado Pago LIVE remains paused for unrelated reasons throughout this task.

### D15 — Permissions: `reward.redeem` reused, no new `reward.apply` permission

Per the task's own explicit instruction, no new permission was created for selecting or applying a reward at checkout. `reward.redeem` (ADR-0018 D18) already models "this actor may cause a reward's benefit to actually be consumed" — attaching a reward to a quote/Sale, and completing a zero-total Sale, both gate on it. Enforced at both the HTTP route layer and the service layer, matching the established defense-in-depth convention.

## Alternatives considered

- **Reserve/lock the entitlement at Sale creation time, not at settlement.** Rejected: this would either block a second cashier from even attaching the same reward to a second (perhaps ultimately abandoned) Sale, or require a timeout-based release mechanism — real complexity for a benefit ADR-0018's own settlement-only-issuance precedent already showed isn't necessary; the settlement-time lock (D7) is sufficient and reuses a proven mechanism.
- **A new `sale_reward_reservations` advisory-lock table.** Rejected in favor of directly locking the entitlement row itself (D7) — a second table would duplicate the exact mutual-exclusion the entitlement row's own lock already provides, with no additional safety.
- **Explicit `reward_combinable_with_*` policy flags on the program.** Rejected for now (D3) — the cascading pipeline placement already produces safe, deterministic stacking without a new schema; a real combinability-restriction need is better designed against an actual business case than speculated in advance.
- **Fake a `$0.00` cash payment for zero-total sales.** Rejected explicitly by the task and by this ADR (D9) — a payment record for money that never moved is a false audit trail.

## Consequences

- **Positive:** the entire redemption-safety story (D7/D8) rests on a single, already-battle-tested lock, not new concurrency-primitive code; refund math needed zero changes (D12); receipt/history needed zero new formatting code (D11).
- **Negative / accepted limitation:** Customer-Detail "redeemed by Sale X" is not yet exposed via a dedicated endpoint (D11); Mercado Pago settlement reconciliation risk (D14) is documented, not resolved, and must be revisited before MP LIVE resumes.
- **Operational:** a zero-total Sale now produces a distinguishable `sale.completed_without_payment` fact for reconciliation tooling to key off (D9).
- **Migration:** additive only — three new `loyalty_programs` columns, two new join tables, one new `sale_reward_usages` table, a widened `sale_discounts.source_type` CHECK; no existing row is altered (D13).

## Validation

Pricing-engine unit tests (`pricing.service.test.ts`) cover all four benefit types, empty/category/product scope semantics (including the deliberate empty-scope-matches-nothing inversion), the single-largest-eligible-line selection rule, and pipeline placement relative to promotions/coupons/manual discounts. Integration tests cover: a quote never mutating reward state; Sale creation freezing a snapshot without redeeming; settlement consuming exactly once; the critical two-Sale concurrent-settlement race resolving to exactly one winner; cancellation releasing the usage row without touching the entitlement; zero-total completion creating no payment/cash-movement row; and a refund against a reward-discounted Sale computing correctly from the frozen snapshot.
