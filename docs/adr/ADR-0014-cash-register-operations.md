# ADR-0014: Cash register operations

- Status: Accepted
- Date: 2026-09-06
- Owners: AS ONE Engineering
- Supersedes: none (extends ADR-0001, ADR-0005, ADR-0009, ADR-0011, ADR-0013)

## Context

TASK 12.7 builds the complete operational cash-register lifecycle: select/open a register, open a session with an entered opening float, take cash sales, record manual cash in/out, see backend-computed expected cash, count and close the drawer, and review cash-cut history. Reconciliation against the existing architecture (before writing any code) found the domain almost entirely pre-specified, not invented fresh:

- `docs/CORE_DATA_MODEL.md` §6.3 already gives exact field lists for `cash_registers`/`cash_sessions`/`cash_movements`; §10 invariant 5 ("at most one open session per register") and invariant 7 ("a sale must reference an open cash session unless a future approved company policy explicitly permits another mode"); §19 open question 5 ("which operations may occur without an open cash session, if any") explicitly unresolved.
- `docs/API_CONTRACTS.md` §5 reserves the exact error codes (`cash_session_required`, `cash_session_already_open`, `cash_session_not_open`, `cash_session_closed`); §6 already lists the six permission codes (`cash_register.read`, `cash_register.manage`, `cash_session.read`, `cash_session.open`, `cash_movement.create`, `cash_session.close`); §16 E038–E048 give exact endpoint contracts; §21.1 gives the exact 3-state `cash_sessions` machine (`open → closing → closed`, with `closing → open` as a documented safe failure).
- `docs/REALTIME_EVENTS.md` reserves the exact event names (`cash_register.created`, `cash_register.device_assigned`, `cash_session.opened`, `cash_movement.created`, `cash_session.closed`).
- `sales.cash_register_id`/`sales.cash_session_id` already existed as reserved, unpopulated nullable columns (ADR-0009) — never real foreign keys until this task.
- `apps/one/lib/features/pos/pos_navigation.dart` already reserves `PosModule.cash` ("Corte de Caja") as the Caja UI's slot, unwired.
- AS POS V1.html's own `modal-cierre-caja` ("Cierre de caja — Arqueo") canonically counts bills/coins before arriving at "Total contado" (its `DENOMINACIONES` array: $1000/$500/$200/$100/$50/$20 bills, $10/$5/$2/$1/$0.50 coins) — confirmed present by reading the file directly, not assumed.

## Decisions

### B1 — CashRegister identity: a device/session-independent drawer

`cash_registers` models the physical drawer, scoped `company → branch → register`, independent of any one cashier or session — a register is never permanently bound to a cashier, and a branch may have more than one register (the dev seed creates exactly one per branch, `CAJA-1`, but nothing in the schema or service layer assumes a branch has only one; see Part U below). `code` is unique per branch while active (`cash_registers_company_branch_code_active_uq`, a partial unique index excluding retired/deleted rows, so a retired code can be reused). An optional `device_id` links a register to a `devices` row — a 2-column FK `(company_id, device_id) → devices(company_id, id)` rather than a 3-column FK including `branch_id`, because `devices.branch_id` is nullable and no unique constraint targets that 3-column combination anywhere else in this codebase either; "the device's branch must match the register's branch" is enforced at the application level (`CashService.createRegister`/`assignDevice`) instead, the same way `payment_terminals` already validates its own device's branch.

### B2 — CashSession lifecycle: the contract's own 3-state machine, real but instantaneous

`cash_sessions.status` is exactly `open | closing | closed` — API_CONTRACTS §21.1's own machine, not a project-invented 2-state or 4-state variant. `closing` is a real, persisted intermediate that a payment-capture-style external dependency could legitimately get stuck in, but *this* implementation's own close command has no external provider dependency (unlike a Mercado Pago capture) — it is pure arithmetic over already-committed ledger facts. So `CashService.closeSession` performs the formal `open → closing` transition and the final `closing → closed` commit inside **one** database transaction: a thrown error anywhere in between rolls the whole transaction back, which *is* the contract's documented "closing → open" safe failure — the session is simply left exactly as it was, still `open`, never visibly stuck in `closing`. At most one session may be `open` or `closing` per register at a time, enforced at the database level: `cash_sessions_register_active_uq`, a partial unique index on `(company_id, cash_register_id) where status in ('open','closing')` — deliberately including `closing`, not only `open`, so a session mid-closure still blocks a second concurrent open.

### B3 — Ledger model: append-only, never a mutable counter

`cash_movements` is append-only — no update or delete path exists anywhere in the service or repository layer, matching the task's own "no delete/edit of posted cash movements" instruction. Every movement carries a `movement_type` from a fixed set — `opening_float`, `cash_sale`, `cash_in`, `cash_out` — and `amount` is always stored positive (`cash_movements_amount_positive_ck`); direction is derived from `movement_type` alone (`cashMovementDirection: {opening_float: 1, cash_sale: 1, cash_in: 1, cash_out: -1}`), never from the sign of the stored amount. `closing_adjustment` — mentioned in the task's own list as a possible category "if canonically necessary" — was deliberately **not** added: a closed session's own `discrepancy_amount` field already records the count/expected difference as a first-class column, so a redundant ledger row would duplicate that fact rather than add a new one. A compensating movement (not an edit) is the only way to correct a posted `cash_in`/`cash_out` — the architecture supports it (nothing prevents posting a corrective `cash_out` against an erroneous `cash_in`), but no dedicated "reversal" UI/endpoint was built in this task; `cash_movements.reversal_of_id` exists as a self-referencing nullable FK for a future reversal feature to use, unpopulated today.

### B4 — Expected-cash formula: folded from ledger facts, never from `sales`

`expected cash = Σ(movement.amount × direction)` over every `cash_movements` row for the session — `CashRepository.expectedCash`/`CashService.summary`, exact `BigInt` fixed-point arithmetic (ADR-0001; `MONEY_SCALE = 10_000n`, matching `numeric(19,4)`), never a floating-point sum and never derived by summing `sales` directly (a session's drawer facts can include non-sale movements a sale-only sum would miss entirely). `GET /cash-sessions/{id}/summary` (E048) is the one read endpoint that exposes this; Flutter displays the backend's result and never recomputes it. The summary intentionally separates `cash_sales_total`/`cash_sales_count` from `cash_in_total`/`cash_out_total` and never folds a card/terminal payment into `expected_cash` at all — a card payment posts no cash movement, so it structurally cannot leak into the drawer total.

### B5 — Cash Sale atomicity boundary: one transaction, four effects

`PaymentService.createCashPayment` — already the sole cash-payment entry point since ADR-0011 — now also resolves and locks the open session (`resolveOpenCashSession`) before doing anything else, and posts the `cash_sale` ledger movement (`CashRepository.postCashSaleMovement`) immediately after `trySettleSale` succeeds, still inside the *same* database transaction as the payment capture, the Sale completion, and (per ADR-0013) inventory consumption. No new transaction boundary was introduced — the existing one transaction now coordinates five effects instead of four: cash Payment captured → Sale completed → inventory consumed (ADR-0013, when applicable) → cash ledger movement recorded → audit/outbox. A thrown error at any point (insufficient inventory, a version conflict, an already-closed session) rolls back every one of them together; proven directly with an integration test that drives an `insufficient_inventory` failure through this exact path and asserts zero captured payment, zero completed sale, and zero cash movement survive.

`cash_register_id` is an **optional** field on `CreateCashPaymentInput`. When supplied, the named register's open session is used (or `cash_session_required` if none). When omitted, the sale's branch's currently-open sessions are looked up (`openSessionsForBranch`): zero throws `cash_session_required`; exactly one is used; more than one throws `validation_error` asking the caller to disambiguate — the register is never silently picked, mirroring this codebase's established "never guess a branch/register" discipline. This keeps every existing Flutter cash-payment call site working unchanged for the common single-register-per-branch case while remaining correct for a future multi-register branch.

### B6 — Tendered/change vs drawer net semantics

The receipt-facing `tendered_amount`/`change_amount` fields (ADR-0011) are completely unchanged — a $29.00 sale where the customer tenders $50.00 still shows "Tendered $50.00 / Change $21.00". The `cash_sale` movement posted to the ledger, however, carries `amount = amountDue` (the sale's own server-computed total, $29.00) — never `tendered`. This is the exact accounting example the task specifies verbatim, proven with an integration test that asserts the persisted `cash_movements` row is `29.0000`, not `50.0000`, and that `expected_cash` after the sale is `opening_float + 29.00`, never `+ 50.00`.

### B7 — Idempotency: a durable, payment-keyed reference boundary

Retrying a cash-payment confirmation (the same idempotency key) must never create two payments, complete the Sale twice, consume inventory twice, or add cash to the drawer twice. `PaymentRepository`'s existing idempotency-key mechanism already prevents the first three; the fourth needed its own guarantee, because a ledger movement is a new row on every `INSERT`, not a keyed upsert. `cash_movements.reference_type`/`reference_id` links a `cash_sale` movement back to the **Payment** it came from — deliberately *payment*-keyed, not *sale*-keyed: a Sale can in principle receive more than one payment (a future split cash+card payment), and keying the uniqueness guarantee by `sale_id` would incorrectly block a second, legitimate cash payment on the same sale. `cash_movements_payment_reference_uq`, a partial unique index on `(company_id, reference_id) where reference_type='payment'`, is the durable, database-level boundary — proven directly with an integration test that attempts exactly that raw duplicate insert and asserts the constraint rejects it, independent of whether the application-level idempotency-key guard is ever bypassed.

### B8 — Branch/register isolation

Every session/register/movement read and write is scoped by `company_id` and the actor's `permittedBranchIds` — `requireBranchAccess` at the route layer, and every repository query filters by branch as well as company. A cash payment on one branch's session structurally cannot post a movement into another branch's session, because `resolveOpenCashSession` only ever looks at sessions for the sale's own `branch_id` — proven with a dedicated integration test. The backend therefore already guarantees isolation independent of anything Flutter does. The Flutter-side policy (binding on the client, backend-enforced regardless): switching branches must never carry an active session across. The topbar's branch switch already reloads the whole POS context (TASK 12.6); the Caja screen must re-fetch `GET /cash-sessions/current` for the newly-selected branch's register on every branch change rather than reuse any previously-loaded session state, so an open session left behind in the old branch stays open there, visible only from that branch, until a human closes it from there. No silent reassignment of a session to a different branch is ever attempted client- or server-side.

### B9 — Close/difference semantics: backend-computed, immutable after close

`declared_closing_amount` (what the cashier counted) is the only money figure the client submits. `expected_closing_amount` is folded server-side from the ledger (B4) at the moment of closure, and `discrepancy_amount = declared_closing_amount − expected_closing_amount` is computed server-side with exact `BigInt` arithmetic — the client never submits a difference, and the schema's `additionalProperties: false` body rejects one if it tried. All three fields, plus `closed_by`/`closed_at`, are populated atomically together (`cash_sessions_closure_fields_ck`: all five null unless `status='closed'`, all five non-null when it is) — a session can never be left in a state where some closure fields exist and others don't. A closed session cannot be closed again (`cash_session_closed`), and its closure fields are never subsequently mutated by any code path in this task.

### B10 — Denomination count (Part J): optional detail behind the same declared total, not a second source of truth

AS POS V1's own close-register modal was confirmed to canonically count bills/coins, so this was implemented rather than skipped. `POST /cash-sessions/{id}/closures` accepts an **optional** `denomination_counts` array (`{value, quantity}` per line); the backend validates every `value` against the exact 11-denomination MXN set V1 itself uses ($1000/$500/$200/$100/$50/$20 bills, $10/$5/$2/$1/$0.50 coins), rejects duplicates and non-integer/negative quantities, and — critically — requires `Σ(value × quantity)` to equal `declared_closing_amount` exactly before persisting anything. It is never accepted as an independent, separately-authoritative total: `declared_closing_amount` remains the one figure that drives `discrepancy_amount`, exactly as it would if the cashier had typed a single number with no breakdown at all. The breakdown is stored as `cash_sessions.denomination_counts` (nullable `jsonb`, only ever populated on an already-closed session — `cash_sessions_denomination_counts_ck`) purely as audit/print detail, mirroring V1's own treatment: V1's persisted `corte` record does not store the breakdown either, only the resulting total. Skipping the breakdown and typing a single counted-cash number remains fully supported and is not a degraded path.

### B11 — Permissions: the six already-reserved codes, nothing invented

`cash_register.read`, `cash_register.manage`, `cash_session.read`, `cash_session.open`, `cash_movement.create`, `cash_session.close` — all six already present in `packages/database/src/seeds/technical-permissions.ts` before this task began, matching API_CONTRACTS §6 exactly. No wildcard, no manual `role_permissions` SQL patch, and no new overlapping code was added. The local development Owner role (`bootstrap-owner.service.ts`) was extended to grant exactly these six, each justified against the specific endpoint the Caja UI and `PaymentService.resolveOpenCashSession` actually call — the same "grant only what the flow needs" discipline the Owner bootstrap already established for `sale.create`/`sale.read`/`payment.create`.

### B12 — Legacy pre-12.7 sales: untouched, no hidden backfill

A Sale completed before this deployment has `cash_register_id`/`cash_session_id` still `null` and no `cash_movements` row referencing it — proven directly against a real historical completed Sale inserted with the exact shape a pre-12.7 completion would have produced. There is no startup backfill, no migration that back-posts historical Sales into a synthetic session, and no worker process that would do so implicitly (mirroring ADR-0013's own Part F "no retroactive backfill" precedent exactly). If a historical reconciliation is ever wanted, it must be a separate, explicit, controlled process — not built here.

### B13 — Deployment/QA seed (Part U): registers only, never a session

`pnpm --filter @asone/api dev:seed-cash-registers` creates exactly one active register (`CAJA-1`) per existing branch of the `inflapark-group` development company, through the real `CashService.createRegister` with a deterministic per-branch idempotency key — guarded by the identical `validateSeedEnvironment` check `seed-pos-catalog.service.ts` already uses (development/test only, loopback host, allowlisted database name by exact match). It never opens a session and never guesses an opening float: "the human must open the drawer manually in QA" is enforced simply by the seed containing no code path that could open one. Re-running it is a safe no-op (`registers: {created: 0, existing: N}`), proven with an integration test.

## Deferred (explicitly out of scope for this task)

- Refunds (any UI or backend endpoint) — no refund/void control was added anywhere in the Caja or POS UI, and no cash movement type or ledger semantics were built to model a refund's drawer effect. A refund's interaction with an open/closed session (does it require an open session? which movement type would model money leaving through a completed sale rather than a manual cash-out?) is a real design question left entirely to that future task.
- Mercado Pago (TASK 12.4B.2) — untouched and still paused; card/terminal payment confirmation gained no cash-session requirement of any kind (B1/B5), since a card payment posts no cash-drawer movement at all.
- A dedicated "reversal" endpoint for a posted `cash_in`/`cash_out` — `cash_movements.reversal_of_id` exists in the schema for this, but no service method or route populates it yet; today a correction is only possible as an ordinary, undistinguished compensating movement.
- Multiple concurrently-open registers per branch in the *default* deployment — architecturally supported end to end (B1, B5's disambiguation-or-error behavior), but the dev seed and Flutter UI both assume the common one-register case; a second register is only reachable today via `POST /cash-registers` directly.
