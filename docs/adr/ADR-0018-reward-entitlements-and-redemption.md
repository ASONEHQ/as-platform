# ADR-0018: Reward entitlements, redemption, and the VIP Pass / 5+1 engine

- Status: Accepted
- Date: 2026-09-04
- Owners: AS ONE Engineering
- Supersedes: none (extends ADR-0017)

## Context

TASK 13.0 (ADR-0017) built the loyalty ledger/account/program FOUNDATION — earn entries accumulate, a balance is always derived, `loyalty_programs.reward_threshold`/`reward_description` existed for progress DISPLAY only — and explicitly deferred actual reward issuance: *"Reward entitlement issuance... deliberately deferred rather than built as an unsafe shortcut"* (ADR-0017, Deferred). TASK 13.1 is that deferred work: a durable Reward Entitlement + Redemption engine, with the first real business scenario being a "5 qualifying stamps → VIP Pass" program.

Forensic search before writing any code confirmed: no `reward_entitlements`/`redeem`/`VIP`/`pass` table, permission, route, or event exists anywhere in the repository prior to this task; `AS POS V1.html` has zero loyalty/rewards/points/stamp code of any kind to reconcile against (already established by ADR-0017's own D16). This domain is genuinely new, exactly like ADR-0017's `customers`/`memberships` were.

The overriding design constraint, stated explicitly by the task and honored throughout: **the engine must stay generic and typed — the "5+1 VIP Pass" business shape must live entirely in program CONFIGURATION (data), never as a hardcoded special case in `rewards.service.ts` or `loyalty.service.ts`.**

## Decisions

### D1 — Reward entitlement is its own durable table, never a customer flag or a balance inference

`reward_entitlements` is a real row per issued reward — never `customers.has_vip_pass = true`, never inferred from `loyalty_ledger`'s current balance at read time. A balance is a live, mutable, derivable number (ADR-0017 D13); an issued reward is a durable FACT that must survive the balance later changing for unrelated reasons (a manual adjustment, a different program's activity on the same account). Proven directly: an integration test earns past a threshold, then performs an unrelated manual loyalty adjustment on the same account, and asserts the previously issued entitlement is completely unaffected.

### D2 — Explicit state machine: `available → redeemed | expired | revoked`, never a transition back

`reward_entitlements.status` is a real enum column (`available`/`redeemed`/`expired`/`revoked`), matching `refunds`'/`sale`'s own established "explicit status enum, never inferred" convention (ADR-0009, ADR-0015). No transition ever leads back to `available` — a redeemed, expired, or revoked entitlement is a closed fact, exactly like a completed `Sale` never reverts to `pending_payment`. `redeemed_at`/`redeemed_by`/`redeemed_branch_id` and `revoked_at`/`revoked_by`/`revoked_reason` are only ever set together with their terminal status (DB-level `CHECK` constraints enforce the pairing), never independently.

### D3 — Program reward configuration: three new typed fields, nothing executable

`loyalty_programs` gains exactly three new columns: `reward_type` (a closed enum, today only `'vip_pass'` — `rewardTypes = ['vip_pass'] as const` in `customers.ts`, the same "reserved-but-minimal, add a value only when a real second reward type exists" precedent as `earning_rule_type`/`product_type = 'kit'`, ADR-0017 D15/ADR-0016 D12), `reward_expiration_days` (optional, `> 0` if present), `reward_repeatable` (defaults `true` — see D4). No arbitrary executable JSON column was added for reward "rules" — the task explicitly warned against this, and a closed typed enum plus a numeric threshold/expiration is the smallest set that expresses "5 stamps → 1 VIP Pass, repeatable, expires in N days" without inventing a rule DSL. `reward_threshold` (already present from ADR-0017) and `reward_type` must be set TOGETHER — a threshold with no reward type would issue nothing on crossing; a type with no threshold has no crossing to trigger it — enforced BOTH by a service-layer pre-check (`LoyaltyService.createProgram`, a clean `validation_error` on mismatch) AND the database's own `loyalty_programs_reward_pair_ck`, the same defense-in-depth ADR-0017 D21 already established for permission checks.

### D4 — Threshold/cycle semantics: recomputed fresh from the ledger, never a stored counter

`cycle_number = floor(cumulativeEarnedUnits / reward_threshold)`, recomputed from a real `SUM(quantity)` read over `loyalty_ledger` (`LoyaltyRepository.cumulativeEarnedUnits`) EVERY time `evaluateAutomaticIssuance` runs — never a separately-tracked running counter that could drift from the ledger it's supposed to summarize. This directly avoids the ambiguous, duplicate-prone `if balance >= threshold then issue` pattern the task explicitly warned against: a durable `cycle_number` gives every possible crossing (1st, 2nd, 3rd...) its own stable, replay-safe identity a unique constraint can key off (D7), rather than one mutable boolean that can't tell a first crossing from a second. A single large earn event that crosses more than one cycle boundary in one settlement (e.g. a high `earn_quantity_per_sale`) correctly loops and issues one entitlement per newly-completed cycle, never only the latest — proven directly.

### D5 — Earn/redeem accounting: Option B — the ledger and balance are left untouched; a durable cycle record is the redemption mechanism instead

Per the task's own explicit choice: for STAMP-shaped programs, "a durable cycle model may be better than resetting." Issuing a reward entitlement (D1) is NOT an `entry_type: 'redeem'` ledger row, and does not reset or decrement the balance — the loyalty ledger stays exactly what ADR-0017 D13 already established: an honest, append-only record of everything ever earned, full stop. The customer's displayed loyalty progress keeps counting up forever; the entitlement history (D1) is the separate, durable record of what was actually ISSUED at each threshold crossing. No loyalty ledger row is ever deleted or silently reset when a reward is issued — proven directly by a test asserting `loyalty_ledger`'s row count and derived balance are unchanged immediately after an automatic issuance fires.

(`loyalty_ledger.entry_type`'s reserved `'redeem'` value, from ADR-0017 D14, therefore remains reserved-but-unexercised in this task too — it would model a POINTS program redeeming points for a catalog benefit directly against the ledger, a genuinely different shape from the entitlement-based model this task builds. Not touched here.)

### D6 — Automatic issuance: inside the same post-settlement transaction as loyalty earning, never before, never on a failed/pending Sale

`RewardsService.evaluateAutomaticIssuance` is called from `PaymentService.applyPostSettlementHooks`, immediately after `LoyaltyService.earnFromSale`, inside the exact SAME database transaction `SalesRepository.trySettleSale` uses to newly transition a Sale to `completed` — the identical transactional hook point ADR-0017 D9 already established for membership activation, extended one step further. A reward can therefore structurally never issue before settlement, never on a `pending_payment`/failed Sale (the hook simply never runs), and never for an inactive program (`evaluateAutomaticIssuance` only ever loops `activePrograms`). Proven directly by a test asserting zero `reward_entitlements` rows exist while the originating sale sits unsettled.

### D7 — Issuance idempotency: a real database unique constraint, proven under real concurrency

This is the mechanism the task called "critical," and it is enforced at the layer that actually matters: `reward_entitlements_company_account_program_cycle_uq`, a `UNIQUE(company_id, loyalty_account_id, loyalty_program_id, cycle_number)` constraint. `RewardsRepository.insertEntitlement` always issues an `ON CONFLICT (...) DO NOTHING` insert; a `null` result means "this cycle already has its entitlement, nothing new to do" — the exact same idempotent-insert pattern ADR-0017 D9/D14 already established for membership activation and automatic earning. Manual issuance (D8) always writes `cycle_number: null`, and Postgres treats every `NULL` as distinct under a unique constraint, so a manual issuance can never spuriously conflict with (or be blocked by) automatic threshold issuance for the same account/program.

Proven under a REAL concurrency test, not a sequential one dressed up as concurrent: two simultaneous calls to `evaluateAutomaticIssuance` against the same already-crossed-threshold account/program (via `Promise.all`, each on its own client/transaction) result in exactly one entitlement row for that cycle — never zero, never two. A second, independent concurrency test proves the same guarantee on the REDEMPTION side (D10).

### D8 — Manual issuance: a distinct, separately-permissioned admin action, no free-text benefit definitions from the client

`reward.issue` (distinct from `reward.read`/`reward.redeem` — see D18) gates `POST /customers/{id}/reward-entitlements`. The caller supplies `loyalty_program_id` + `reason_code` + an optional `expires_at` override — never a free-text "benefit" description or a client-chosen `reward_type`; the actual reward type is always read server-side from the program's own configuration (`program.rewardType`), so a manually issued entitlement is exactly as typed and constrained as an automatically issued one, just triggered administratively instead of by threshold-crossing. Idempotency-key gated like every other mutation in this codebase; `reason_code` is recorded in `audit_log`'s own metadata (never in the durable outbox payload, matching ADR-0017 D7/D22's minimal-payload convention) so a manual grant is always attributable and auditable.

### D9 — Redemption is server-authoritative; Flutter never computes eligibility locally

`POST /reward-entitlements/{id}/redeem` (`reward.redeem`) is the ONE place redemption eligibility is decided — company/existence/ownership, customer-active status (D17), current status, and lazy expiry (D14) are all re-checked server-side on every call, inside a row-locked transaction (D10). Every entitlement API response carries both the raw persisted `status` AND a live-computed `effective_status` (`rewards.types.ts`'s `effectiveStatus()`, a pure function of `status`/`expires_at`/now) — Flutter is required to key every "can this be redeemed right now" decision off `effective_status`, never off `status` alone and never off a locally recomputed expiry check (Part N/V of the task spec). This mirrors ADR-0017 D11's "one server-authoritative validation endpoint, Flutter never computes this itself" precedent exactly.

### D10 — Redemption idempotency and concurrency: row lock + idempotency key, proven under real concurrency

`redeem()` runs inside `RewardsRepository.lockEntitlement`'s `SELECT ... FOR UPDATE` — the same row-lock-based mutual-exclusion mechanism `CashService`/`RefundsService` already use for their own single-writer-at-a-time invariants — combined with the standard idempotency-key mechanism (a replay with the SAME key returns the SAME already-redeemed result, never a second redemption, never an error). A DIFFERENT idempotency key racing the SAME entitlement is rejected with `reward_already_redeemed` once the first has committed. Proven under a real concurrency test: two concurrent redeem attempts (different idempotency keys, `Promise.all`) against the same available entitlement result in exactly one success and one `reward_already_redeemed` rejection — never two successes, never zero.

### D11 — Redemption is deliberately separated from benefit application

Marking an entitlement `redeemed` NEVER automatically creates a free Sale, a negative-amount Sale, a fake payment, a fake refund, a cash movement, or an inventory movement — the task explicitly named every one of these as things NOT to invent, and none is invented. TASK 13.1 implements entitlement issuance, validation, and redemption in full; applying the redeemed reward's actual commercial benefit at the POS (e.g. waiving a specific line item's price) is EXPLICITLY DEFERRED — no canonical pricing-integration rule exists yet for how a redeemed entitlement should interact with `promotions`/`pricing.service.ts` at checkout, and inventing one here would be exactly the kind of unscoped commercial rule the task warns against. A cashier redeems the entitlement (a durable, auditable fact: "this VIP Pass was used, here, now, by this actor") and then applies whatever discount/pricing action the existing checkout flow already supports through its own existing, already-permissioned mechanisms (e.g. `discount.apply`, ADR-0016 D11) — manually, today. See Deferred.

### D12 — VIP Pass is a reward TYPE on an entitlement, never a customer flag; its QR is a distinct concept from the customer's own QR

There is no `customers.has_vip_pass` column and never will be under this model (D1) — "VIP Pass" is simply the current, and so far only, value of `reward_entitlements.reward_type`. Its presentation token (`reward_entitlement_tokens`, D14/X) is a SEPARATE table from `customer_qr_tokens` (ADR-0017 D16), deliberately: a customer QR identifies the CUSTOMER (used for lookup/attach-to-transaction); a reward token identifies one specific ENTITLEMENT (used to present/redeem that one reward). The two are never rendered from the same component, never resolved through the same endpoint, and neither token's payload contains any trace of the other's identifier. `reward_entitlement_tokens` mirrors `customer_qr_tokens`'s own generation/validation mechanics exactly (D14) — a CSPRNG-random opaque value, at most one active token per entitlement (a real partial unique index), revoke-then-issue rotation, cross-company resolution explicitly rejected — because that mechanism was already proven correct in ADR-0017 D16, not because the two concepts are the same thing.

### D13 — The "5+1" business shape lives in dev/QA seed data only, never hardcoded in engine code

`dev:seed-loyalty-rewards` (`apps/api/src/development/seed-loyalty-rewards.service.ts`) creates one concrete program — "Sellos VIP (5+1)": `unit_type: 'stamp'`, `reward_threshold: 5`, `reward_type: 'vip_pass'`, `reward_repeatable: true` — entirely as DATA, through the same real, generic `LoyaltyService.createProgram` any company's own admin console would call. No string `'5'`, `'VIP'`, or `'vip_pass'` appears anywhere in `rewards.service.ts`'s or `loyalty.service.ts`'s actual control flow as a special case — `evaluateAutomaticIssuance` treats every reward-bearing program identically regardless of its threshold value or reward type. "5 stamps earn a pass to use on the NEXT visit" is modeled exactly as stated: the entitlement is issued the moment the 5th qualifying stamp settles, available starting then — never an automatic free CURRENT transaction, since issuance happens inside the SAME settlement that earned the 5th stamp, strictly after that Sale is already `completed` (D6), with no mechanism anywhere that discounts or waives the sale that triggered the crossing.

### D14 — Expiration: optional, lazily evaluated, no scheduler

`reward_entitlements.expires_at` is optional (`null` means "never expires"). No scheduled job, cron, or background worker ever transitions a row to `'expired'` — none was built, matching the task's explicit "no fake scheduled jobs" instruction. Instead, `effectiveStatus(row, now)` (D9) is a PURE function computing the live, display-time answer ("is this actually redeemable right now") without persisting anything — used everywhere a caller needs to know current eligibility, including every list/detail response. The ONE place a stale `available` row is actually mutated is inside `redeem()` itself: if someone attempts to redeem a `status: 'available'` row whose `expires_at` has already passed, that single transaction flips it to `'expired'` in the database (a real DB-level status transition, not merely a computed display value) and THEN rejects the redemption with `reward_expired` — so the persisted status only ever needs to catch up with reality at the one moment it's actually acted on, never on a schedule. `reward.expired` (§11.13) is published for this transition exactly like any other committed fact — including when it's an idempotency-key replay of an already-expired result, since the transition itself was only ever recorded once.

A genuine bug was found and fixed while writing this task's own integration tests: the first implementation called `markExpired(...)` and then immediately `throw`n the `reward_expired` error FROM INSIDE the same all-or-nothing `RewardsRepository.transaction(...)` the whole redeem attempt runs in — since a thrown error rolls back everything the transaction did, `markExpired`'s own `UPDATE` was silently undone right along with it, and the row's persisted `status` never actually left `'available'`, contradicting this very paragraph's claim (and the task's own explicit design). Fixed by having that branch RETURN the now-`'expired'` row instead of throwing — letting the transaction commit the transition for real — and having `redeem()`'s caller-facing wrapper inspect the committed result AFTER the transaction returns, raising `reward_expired` there instead. A same-key replay against the now-committed `'expired'` row takes the identical post-commit path and rejects identically every time. Caught specifically because this task, unlike a purely unit-tested pass, asserted the actual persisted database row's status after a redeem attempt on an expired entitlement, not merely the HTTP response — the same category of gap ADR-0017 D14 already found once in the sibling idempotency mechanism.

### D15 — Revocation: a separate permission, a mandatory reason, cannot revoke an already-redeemed entitlement

`reward.revoke` (distinct from `reward.issue` — an admin authorized to grant rewards is not automatically authorized to revoke them, though in practice the local dev owner seed grants both) gates `POST /reward-entitlements/{id}/revoke`. A `reason` is required and non-blank (mirrors `refund.approve`'s/`customer_membership.cancel`'s own "a destructive-ish administrative action always records why" convention). Revoking an already-revoked entitlement is a safe no-op — it returns the current (already-revoked) row unchanged rather than erroring, since the caller's intent ("this should not be usable") is already satisfied. Revoking an ALREADY-REDEEMED entitlement is explicitly rejected (`reward_already_redeemed`) — a reward that was already used cannot be retroactively un-issued; if a redemption was made in error, that is a separate, undefined-in-this-pass administrative remedy (see Deferred), not silent revocation of history.

### D16 — Refund interaction: explicitly deferred, no silent destructive behavior invented

If a Sale that contributed a qualifying earn (and, transitively, a threshold crossing) toward a reward entitlement is later refunded, that entitlement is NEVER automatically revoked and the underlying loyalty ledger entry it derived from is NEVER automatically reversed in this pass — mirroring ADR-0017 D20's identical "no automatic membership revocation on refund" decision, extended to rewards for the same reason: no canonical commercial rule for "should a refunded purchase retroactively invalidate a reward that was already issued (and possibly already redeemed) from it" exists, and the task explicitly forbids inventing one here. No ledger row, no entitlement row is ever deleted or silently mutated as a side effect of a refund. If a business needs to correct this manually, `reward.revoke` (D15) remains the administrative remedy for an unredeemed entitlement — but nothing automatic exists, and this is a deliberate, documented limitation, not an oversight.

### D17 — Customer archival: history is retained; an inactive customer cannot redeem, but can still be viewed

Mirroring ADR-0017 D18 (`customers.status`, never a destructive delete): an archived or inactive customer's full reward-entitlement history remains fully readable via `GET /customers/{id}/reward-entitlements` — nothing is hidden or deleted. However, `redeem()` explicitly checks `customer.status === 'active'` and rejects (`reward_not_available`) otherwise — an archived/inactive customer cannot REDEEM a reward, a deliberate server policy choice (not a hard block on ever viewing the entitlement), consistent with treating archival as a soft, history-preserving state rather than a hard account freeze that would also need to explain itself in read paths.

### D18 — Permissions: four new codes, mirroring the established three/two-tier shape

`reward.read` — the cashier's own day-to-day lookup (Customer Detail's rewards section, POS reward lookup). `reward.redeem` — the checkout-time consuming action. `reward.issue`/`reward.revoke` — admin-only (manual grant, fraud/correction). A cashier role is granted `reward.read` + `reward.redeem` ONLY, mirroring `discount.apply`/`membership.issue`'s own established "separate the checkout action from the admin action" shape (ADR-0016 D11, ADR-0017 D21) — no separate cashier-role seed file exists in this codebase to update (permissions are granted per company/role through the existing admin role-management surface); the local dev owner seed (`bootstrap-owner.service.ts`) was extended to grant all four, since the dev owner identity is the admin identity local QA runs as, not a stand-in for a real cashier's actual grant set. Every route checks the permission BOTH at the HTTP layer (`requirePermission(authentication, auth, ...)`) AND again inside the service layer (`context.actorPermissions.includes(...)`), matching ADR-0017 D21's defense-in-depth convention exactly — verified directly by the routes-level permission tests.

### D19 — Idempotent replay decoding: JSON-serialized, so every non-JSON-native runtime type (`Date`, `bigint`) must be explicitly reconstructed (TASK 13.1A)

D7's `decodeEntitlement()` fix was module-local; TASK 13.1A is the forensic sweep of the same pattern everywhere else `idempotent()` is used. `idempotency_keys.response_body` is real JSON — `JSON.stringify` on a successful mutation's result already turns every `Date` field into an ISO string and every `bigint` into a decimal string, since JSON has neither type natively. On REPLAY, that JSON is read back and handed to a caller-supplied `decode` function; a bare `(value) => value as SomeRow` cast (this codebase's inherited shorthand in several modules) does not actually convert anything — it just tells TypeScript to believe the lie. The bug is invisible to a service-level test (`.status`/`.id` never invoke `.toISOString()`) and was found only because TASK 13.1's own Real Local QA walkthrough drove a genuine HTTP round-trip against the live server.

The sweep enumerated every `idempotent()` call site in the API (23 files) and classified each by what it actually persists and decodes:

- **Already safe by real decoder** — `sales`, `payments`, `refunds`, `cash`, `product-catalog`, `product-options` each already reconstruct with `new Date(...)`/`BigInt(...)` in a local `decodeX()` function; `inventory.repository.ts`'s `location()` mapper does the same. Untouched.
- **Already safe by construction** — `inventory-drafts`, `inventory-counts`, `reservation`, `inventory-transfers` (delegates to `inventory-drafts`), `inventory-reversal`/`inventory-posting` (delegate to `inventory-drafts`), and `inventory-repair` all persist the FINAL, already-`.toISOString()`'d HTTP JSON shape at write time (a `*Json()` helper), never a typed row with live `Date` fields — there is nothing to reconstruct on replay because nothing was ever serialized lazily. Untouched.
- **Genuinely affected, fixed** — `customers.service.ts` (`decodeCustomer`), `loyalty.service.ts` (`decodeProgram`, `decodeLedgerEntry`), `memberships.service.ts` (`decodePlan`, `decodeMembership`), `promotions.service.ts` (`decodePromotion`, `decodeCoupon`) — each given a real local decoder mirroring `decodeEntitlement()`'s own shape. `catalog.repository.ts`'s `category()`/`brand()` mappers were a FIFTH affected site the original bug report didn't name: they serve BOTH a fresh `pg` row (already a real `Date`) and the replay path, and did a bare pass-through for `created_at`/`updated_at`/`deleted_at` — fixed by wrapping in `new Date(...)` (correct for either input), matching `inventory.repository.ts`'s own `location()` precedent for a mapper serving both roles.
- **A dead, ALREADY-WRONG decoder pair, removed rather than wired in** — `promotions.repository.ts` had its own unused `decodePromotion`/`decodeCoupon`, exported but never imported anywhere. They cast to the snake_case DB-row shape (`PromotionDb`/`CouponDb`), which is NOT what `idempotent()` actually persists (the camelCase `PromotionRow`/`CouponRow` `create()` returns) — using them as-is would have produced a silently mis-mapped row (e.g. `companyId: undefined`), a worse failure mode than the one being fixed. Deleted; `promotions.service.ts` now has its own correct local decoders instead.
- **A second, unrelated idempotency bug found by the same HTTP replay test** — `PromotionsService.createPromotion`/`createCoupon` hashed the server-RESOLVED `id` (`input.id ?? randomUUID()`) rather than the caller-supplied one, so a genuine same-key replay (client omits `id`) computed a DIFFERENT hash every call and was rejected as a conflicting request instead of replaying — the exact class ADR-0017 D14 already found and fixed once in `customers`/`memberships`/`loyalty`, missed here. Fixed to hash `input.id ?? null`, matching `SalesService.createSale`'s own established convention.

Regression coverage: `apps/api/src/modules/idempotency-replay-http.integration.test.ts` boots a real Fastify app with real, database-backed services (only the auth layer is faked, mirroring `settings.routes.integration.test.ts`'s own established pattern) and drives genuine `app.inject()` create-then-replay round-trips against all five fixed sites, asserting a clean 200/201 (never the 500 this bug produced), well-formed ISO date strings, identical replayed values, and exactly one underlying row — plus a distinct-key/distinct-body non-replay case and a same-key/different-body deterministic-conflict case. `rewards.integration.test.ts` gained matching `toBeInstanceOf(Date)` assertions on its own two replay tests, closing the same gap at the service level for the module where it was first found.

One pre-existing inconsistency was observed, not fixed (out of this task's surgical scope): a same-key/different-body conflict is `validation_error`/400 in `customers`/`loyalty`/`memberships`/`promotions`/`rewards`, but `idempotency_conflict`/409 in the `inventory`-family repositories — both are deterministic and correct within their own module, they simply disagree with each other on which reserved code to use for the identical scenario.

## Deferred (explicitly out of scope for this task)

- **POS benefit application** (D11) — redemption records the fact; actually waiving/discounting a specific checkout line item as a consequence of a redeemed entitlement is separate future work pending a canonical pricing-integration rule (how it composes with `promotions`/manual `discount.apply`, whether it's automatic or cashier-triggered, etc.).
- **Refund → reward/loyalty reversal** (D16) — no automatic reward revocation or ledger reversal on refund; a known, documented limitation.
- **Apple/Google Wallet live provider integration** — the reward presentation token (D12) is a stable identifier a future pass COULD use as a Wallet pass serial number; nothing further is built or stubbed toward it, matching ADR-0017 D17's identical stance on the customer QR.
- **QR scan/resolve staff UI** — `POST /reward-entitlements/resolve-token` exists server-side (Part T's minimal API surface); a dedicated scanning UI/device flow for staff to scan a presented reward QR was not built in the Flutter app this pass — see the Flutter section of the TASK 13.1 final report for what WAS built (Customer Detail display, POS redeem button) versus this specific piece.
- **A second reward type** — `reward_type` is a closed enum with exactly one value (`'vip_pass'`) today; adding a second (e.g. a flat discount-percent reward, a free-item reward) is real future work, not silently pre-built as unused columns.
- **Customer-facing self-service redemption** — CLIENTE mode may DISPLAY a customer's own reward status; actually triggering a redemption always requires cashier authorization through the same server-side `reward.redeem` gate CAJERO mode uses — no self-service redeem path exists anywhere.
- **Mercado Pago** — untouched and still paused; nothing in this task's scope touches payment provider configuration.
