# Pre-Launch Deep Audit — TASK 16.23A (2026-09-22/23)

**Branch:** `release/as-pos-v1`. **Starting SHA:** `c454443` (TASK 16.22 checkpoint). **Method:** an adversarial, evidence-only audit — six parallel investigation agents (plus their own sub-agents, ~20 total) each given read-only access to a bounded slice of `apps/api/src/modules/` and `apps/one/lib/features/pos/`, instructed to find real, demonstrable defects and quote exact `file:line` evidence, never invent or hide a finding. This document records what was actually checked and what was found — a code path not listed below was not part of this pass and should not be assumed clean.

No production data was written. No tenant was created. No migration was run. No infrastructure was touched. Everything in this document comes from reading code, reading test files, and running tests locally (backend against a dedicated `asone_test` Postgres database, Flutter's own widget/unit suite) — never from writing to `api.asone.mx`/`app.asone.mx`.

## Legend

- **VERIFIED** — proven by an automated test that actually ran (and passed) during this audit.
- **INSPECTED** — proven by direct reading of the real source (route handler, schema, SQL), not merely inferred from a name or a doc comment.
- **NOT TESTED** — the code path exists and was read, but no automated test exercises it; risk is unquantified.
- **BLOCKED** — could not be checked at all in this pass (needs production credentials, a live browser session, or is out of scope).

## Multi-tenant isolation review (Phase G) — the headline result

**Zero confirmed cross-tenant or cross-branch data leaks were found anywhere in the backend.** Every one of ~200+ repository methods reviewed across sales, catalog, inventory (8 files), purchasing, suppliers, parties, payments, refunds, people, memberships, loyalty, access, rewards, reports, cash, and admin filters reads/writes by `company_id` (and `branch_id`/`permittedBranchIds` for branch-owned entities), and every route derives `companyId`/`permittedBranchIds` exclusively from the authenticated session (`requireAuthenticatedUser` → `AuthService.authenticate(bearerToken)`), never from client-supplied body/query/path values. A handful of repository methods rely on the *calling service* to have already branch-checked the row moments earlier in the same transaction rather than filtering `branch_id` in their own SQL (documented in each sub-audit as "fragile-by-convention, not currently exploitable") — these are noted as hardening candidates, not defects.

**Real gap: test coverage, not enforcement.** A dedicated coverage pass (Phase AA) found that while the RBAC *enforcement code itself* is confirmed correct by direct reading, the *integration test suites* have **zero HTTP-level 403 (permission-denial) coverage** for: sales, held-sales, inventory (all 7 files), payments, refunds, cash (all 8 files), customers (pre-fix), memberships (pre-fix), loyalty (pre-fix, some), rewards (pre-fix, some), promotions, operational-areas, and branch-consolidation. Parties covers only 3 of ~20 gated endpoints and is missing its two highest-risk codes (`party.cancel`, `party.payment.record`) entirely. Several of these modules DO have unit-level route-wiring tests (`*.routes.test.ts`, mocked service/DB) that cover the same ground at a shallower layer. This is a real, worthwhile follow-up (dozens of new integration tests), too large to complete inside this overnight pass — the 4 modules with an actual bug (F-01) were fixed and given real regression coverage; the rest remain a documented gap.

Also confirmed clean by direct reading and cross-referenced against ~150 route registrations: **RBAC enforcement itself** (Phase H) — every mutating/sensitive-read route calls a permission check strictly before touching the database, no permission-code typos against the canonical 60-code `technicalPermissionCodes` list, no case where the frontend hides a button with no matching backend enforcement.

## Money & rounding (ADR-0001) — full result

Confirmed clean, BigInt-exact throughout: `sales.service.ts`, `promotions/pricing.service.ts` (the one canonical pricing/discount engine), `refunds.service.ts` (including an explicit `refund_limit_exceeded` check — a refund can never exceed its original sale), `cash.service.ts`, `reports.service.ts`, `dashboard.service.ts`, `memberships.service.ts` (delegates all arithmetic to the pricing engine, never computes money itself), and the Flutter `money.dart`/`sale_session.dart` (every payment-flow amount is parsed from a real backend response; the one client-side pre-quote estimate is explicitly documented as never authoritative). Two genuine float round-trips found and fixed: F-02 (party snack quantity, real money math) and F-03/F-04 (print-only cash-cut display). Rounding policy (round-half-up, documented in `docs/adr/ADR-0001-money-and-rounding.md`) is applied identically everywhere checked.

## Snapshot / idempotency / concurrency — full result

All CLEAN, no findings. Sales line items freeze `name_snapshot`/`unit_price`/`tax_snapshot` at completion (never re-read from a later-edited product). Membership benefit discounts freeze into `sale_discounts` at checkout (a later plan edit never rewrites a past sale). Refunds recompute strictly from the original sale's own frozen snapshot. Party reservations' snapshot immutability was re-confirmed (already live-verified in TASK 16.22). All 5 sensitive mutating actions checked (sale creation, payment recording, reservation creation, customer creation, product save) have a real backend idempotency-key mechanism (`pg_advisory_xact_lock` + a persisted `idempotency_keys` row, not just an app-level check) AND a frontend `_busy`-style double-submit guard (35+ call sites confirmed). Every concurrency-sensitive path checked (room double-booking, inventory stock deduction, cash-session opening, coupon redemption limits) is backed by a real Postgres-level guarantee (a GIST exclusion constraint, `SELECT ... FOR UPDATE`, or a partial unique index) — never a bare app-level check-then-write race.

## Security / logging / error contract — full result

No real secrets found committed anywhere (only clearly-labeled local-dev fixtures with fictitious values). Structured logger redacts passwords/tokens/cookies/connection-strings and query strings; automatic Fastify request logging is disabled. No access/refresh token ever appears in a URL on either side; the Flutter client keeps the access token memory-only and relies on an `HttpOnly`/`SameSite=Strict` cookie for refresh — the correct pattern. Error responses are consistently shaped and status-coded across every module sampled (with the F-01 exception, now fixed, and F-09's cosmetic code-reuse). Global error handler never leaks a stack trace or raw DB error to a client. Zero genuine `TODO`/`FIXME`/`HACK` markers exist in production source; every `mock`/`fake`/`stub`/`placeholder` hit traced to a deliberate, documented mechanism except F-07 (QR login tab).

## Provisioner findings (Phase AE) — read-only, not executed

`apps/api/src/provisioning/production-owner.cli.ts` / `production-owner.service.ts` fully reviewed, **not run**.

- **Required flags:** `--company-legal-name`, `--company-slug`, `--owner-name`, `--owner-email`.
- **Optional flags:** `--company-display-name`, `--company-timezone` (default `America/Mexico_City`), `--company-currency` (default `MXN`), `--company-locale` (default `es-MX`), `--branch-name` + `--branch-code` (both required together or neither), `--branch-timezone`, `--database-url` (else `DATABASE_URL` env), `--yes` (skips the interactive confirmation prompt).
- **Password:** interactive masked prompt (recommended) or `PROVISION_OWNER_PASSWORD` env var when non-interactive — never echoed, never logged, hashed once with `argon2id`.
- **If the company slug already exists:** refuses loudly (`already_provisioned`-style `ProvisioningInputError`) — deliberately not idempotent/upsert; re-running against an already-provisioned slug is always an honest error, never a silent no-op or a second write.
- **Transaction/rollback:** the entire company + branch (if given) + owner user + membership + Owner role + full current permission grant + audit-log row is written inside one database transaction — any failure at any point rolls back everything, nothing partial is left for a retry to trip over.
- **Permissions:** refuses loudly if the `permissions` table is empty (i.e. `db:seed` hasn't run) rather than silently provisioning a powerless owner; otherwise grants the Owner role every permission code that currently exists.
- **Email uniqueness:** not specially handled by this class — relies on the database's own `users_normalized_email_uq` unique constraint; a duplicate email across companies would surface as a raw Postgres constraint-violation message via the CLI's generic catch-all, not a friendly `ProvisioningInputError` (minor polish gap, not blocking — this is an operator-run CLI, not an HTTP endpoint).
